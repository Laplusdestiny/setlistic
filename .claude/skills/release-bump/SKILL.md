# release-bump

PR を作る前に、この手順でバージョンと更新履歴をそろえる。上げ幅と文は毎回オーナーに提案し、了承を得てから反映する。バージョンを持っているのは次の2か所だけ。

| ファイル | 内容 |
| --- | --- |
| `package.json`（と `package-lock.json`） | `version`。最新の更新履歴とそろえる |
| `src/lib/release-notes.ts` | `RELEASES`（新しい順）。ヘルプの「更新履歴」（`/help#releases`）に表示される |

`src/lib/release-notes.test.ts` が「最新の更新履歴＝`package.json` の version」「新しい順」を検査するので、片方だけ変えると CI が落ちる。

## 1. main に追いつく

ほかの PR が先にバージョンを上げていることがあるので、上げる前に最新の main に載せ直す。

```bash
git fetch origin
git rebase origin/main
```

いまのバージョンは `RELEASES[0].version`（＝`package.json`）で確かめる。

## 2. 上げ幅を決める

`git log origin/main..HEAD` と `git diff origin/main...HEAD --stat` で、この PR の変更を読む。基準は「利用者の画面や動きが変わるか」。

| 変更 | 上げ幅 | 例 |
| --- | --- | --- |
| 新しい機能、今ある機能の動きや見た目が変わる | **minor**（0.7.0 → 0.8.0） | `feat:`、URL・仕様の変更 |
| 不具合の修正だけ | **patch**（0.7.0 → 0.7.1） | `fix:` |
| 利用者から見て何も変わらない | **上げない** | `test:` `docs:` `ci:` `refactor:`、開発用ファイル・README・`CLAUDE.md` だけの変更 |

- 1つの PR に種類が混ざっているときは、いちばん大きいものに合わせる（新機能＋修正なら minor）
- 接頭辞は目安。`chore:` でも公開URLが変わるなど利用者に見えるなら上げる。`feat:` でも管理者向けの見えない内部処理だけなら、上げるかどうかをオーナーに確かめる
- **major（1.0.0 など）は自分で決めない**。データの形が変わって書き出したファイルが読めなくなる、など大きな変更のときはオーナーに相談する
## 3. オーナーに提案して確かめる

**毎回、上げる前にオーナーへ案を示し、了承を得てから 4 以降に進む**（自分の判断だけで上げない）。案は次の形でチャットに書く（AskUserQuestion のポップアップは使わない）。

```markdown
バージョンの案：0.7.0 → **0.8.0**（minor）
理由：曲の詳細に「同じアーティストの曲」を足した（新機能）

更新履歴の案：
- 新機能：曲の詳細から、同じアーティストの曲を探せるようにしました
- 不具合の修正：iPhone で、検索欄が画面からはみ出ていたのを直しました
```

- 据え置きにする場合も「据え置き（理由）」として示して確かめる
- 上げ幅・文の直しを言われたら、それに合わせて案を出し直す

据え置きに決まったら 4〜5 を飛ばし、PR の本文に「バージョン：据え置き（利用者に見える変更なし）」と書く。

## 4. バージョンを上げる

```bash
npm version <新しいバージョン> --no-git-tag-version
```

`package.json` と `package-lock.json` の両方が変わる。タグは作らない。

## 5. 更新履歴を足す

`src/lib/release-notes.ts` の `RELEASES` の**先頭**に、3 で了承された内容を1件足す。

```ts
{
  version: "0.8.0",
  date: "2026-10-25", // 上げた日（YYYY-MM-DD）
  changes: [
    { kind: "feature", text: "曲の詳細から、同じアーティストの曲を探せるようにしました" },
    { kind: "fix", text: "iPhone で、検索欄が画面からはみ出ていたのを直しました" },
  ],
},
```

- `kind`：`feature`（新機能）・`change`（今ある機能の変更）・`fix`（不具合の修正）
- 書くのは**利用者向けの言葉**。PR の技術的な説明（コンポーネント名、CSS、`z-index`、RLS など）は書かない
  - 文末は「〜できるようにしました」「〜を変えました」「〜を直しました」
  - 不具合は「どの端末で・何が起きていたか」が利用者に分かるように書く（例：「Android で、並び替えメニューがタグの下に隠れて押せなかったのを直しました」）
  - PR 番号や Issue 番号は書かない（利用者は GitHub を見ない）
  - 1件1文を目安に、補足が要るときだけ2〜3文にする
- 利用者に見えない変更（テスト・リファクタリングなど）が同じ PR に入っていても、更新履歴には書かない
- ヘルプの本文（`src/app/help/page.tsx`）の使い方の説明が変わる機能なら、そちらも直す

## 6. 確かめてコミットする

```bash
npx vitest run src/lib/release-notes.test.ts src/app/pages.test.tsx
npm run format:check
```

機能の変更とは分けて、1コミットにする。

```
chore: バージョンを 0.8.0 に上げ、更新履歴を足す
```

## 7. PR の本文に書く

PR の本文に次の節を入れる。

```markdown
## バージョン
0.7.0 → **0.8.0**（minor：新機能を追加したため）

更新履歴に足した内容：
- 新機能：曲の詳細から、同じアーティストの曲を探せるようにしました
```

## PR を出したあと

- **ほかの PR が先にマージされて競合したとき**：`git rebase origin/main` で載せ直し、`RELEASES` の先頭を新しい main の次のバージョンに付け直す（例：main が 0.8.0 になったら、この PR は 0.9.0 にする）。`package.json` は `npm version` で付け直す。PR の本文の「バージョン」も直す
- **レビューで内容が変わったとき**：上げ幅と更新履歴の文を見直し、変えるなら 3 と同じくオーナーに確かめる
- **マージが上げた日より後の日になったとき**：日付は直さなくてよい（直すなら、マージ前に `date` を変える）
